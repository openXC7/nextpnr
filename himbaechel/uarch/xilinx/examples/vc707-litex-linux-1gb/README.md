# VC707 LiteX VexRiscv-SMP SoC, 1 GB of DDR3 (xc7vx485tffg1761-2)

A 32-bit RISC-V Linux SoC: VexRiscv-SMP in LiteX's `linux` variant, with a
64-bit DDR3 interface giving the full **1 GB** of the VC707's SODIMM, a 128 KiB
L2, SGMII Ethernet and an SD card controller.

    cells          26524
    RAMB36E1           6
    RAMB18E1          93
    DSP48E1            4
    CARRY4           630
    MMCME2_ADV         3
    GTXE2_CHANNEL      1

Generated by:

    vc707_litex.py --cpu-type vexriscv_smp --cpu-variant linux --cpu-count 1 \
      --hardware-breakpoints 0 --with-wishbone-memory --with-ddr --with-ddr64 \
      --with-ethmin-phy --with-sdcard --l2-size 131072 --with-led-chaser \
      --flow openXC7 --no-compile-gateware

"SMP" here names the *interrupt fabric*, not the core count: the VexRiscv-SMP
cluster carries a RISC-V CLINT and PLIC where the plain single-core variant has
neither.  `--cpu-count 1` is deliberate, and `nproc` on the booted board
correctly reports 1.

It answers to `10:e2:d5:53:4d:50`, the same MAC as `vc707-litex-linux-smp`,
because it is the same SoC family and boots from the same TFTP directory.

## Why this one is in the gate

Every other stretch entry asks only whether P&R completes.  This one asks
whether it **meets timing**, because it is the design that historically did
not.  Its DDR controller domain, `main_crgddr_clkout_buf0`, is constrained at
100 MHz and the open flow reached only 75.59 MHz -- a bitstream that places,
routes, assembles and configures with DONE asserted, and then miscomputes on
hardware.

A measured interconnect delay model closes it, and this entry exists to keep
it closed:

    baseline (tuned delay formula, timingweight 60)              75.59 MHz  FAIL
    + measured delay matrix, timingweight 100                  103.08 MHz  PASS

so the entry runs with `-o delay-matrix=build --placer-heap-timingweight 100`
rather than the gate's default placer flags.  The router CONVERGES here
(overuse 36127 -> 0 in 29 iterations); with the old separable formula it
DIVERGES on this netlist -- overuse floors around 5000 and climbs -- because
that formula charges a diagonal the sum of both legs and two tiles twice one
tile, when the fabric's bent wires and quads do neither.  See
`docs/measured-delay-matrix.md` in xc7-bitstream-tools.

The out-of-window pricing matters most here, and it is where an earlier version
went wrong: it must be measured, not a scaled formula.  The measured marginal
rate is anisotropic -- about 7 ps/tile horizontally but 12.8 vertically -- and
the DDR datapath is vertical, so mispricing the vertical rate lets the placer
spread it and the router cannot recover.  (An earlier build fitted a single
scale to the formula and, through a cache round-trip that dropped it, once
reported 106.50 -- higher, but an artifact of overpricing every long
connection threefold, and not reproducible under the flags this entry
actually runs.)

A second, independent route to the same result is
`--placer-heap-timingweight 60 --router2-slack-order --router2-tmg-ripup`,
which reaches 101.90 MHz.  Those two router flags only work as a pair.

## Provenance

This netlist is from a build that was flashed to a VC707 and watched boot to a
Linux shell over NFS, not from a configuration that merely elaborates:

    MemTotal   1032604 kB
    kernel     6.9.0+
    isa        rv32ima
    nproc      1

The netlist carries the BIOS: yosys resolves the ROM's `$readmemh` into RAMB
INIT words at synthesis time, so nothing here needs a RISC-V compiler.
2.3 MB gzipped in the tree, 41 MB raw.
